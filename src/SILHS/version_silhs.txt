    Add P3 microphysics with SILHS ice support (#1454)
    
    * Add P3 microphysics to CLUBB standalone (warm rain, no ice yet)
    
    Issue #1359 asks for P3 in CLUBB so it can later be ported to JAX.
    microphys_scheme = "p3" now calls P3 v4.0.7-HM-TurbCC from the
    CM1R21-SDM rico_turb branch (6702544) for all columns. P3 reads the
    two-moment ice lookup table from CM1 release 21.0, added under
    input/p3_lookup_tables. The P3 source is unchanged except for the .F90
    name and allocating its unused 3-moment and multi-category tables only
    when needed (about 80 MB per executable in debug builds).
    
    P3 runs with one ice category, two-moment ice and the Seifert-Onishi
    option off. CLUBB carries only rain (rrm, Nrm), so a run stops if P3
    forms ice. CLUBB keeps diagnosing cloud water: P3 receives grid-mean
    rcm and Ncm, sediments rain and droplets itself, and its changes return
    as tendencies. thlm_mc uses CLUBB's constants, as for KK, so P3's
    condensation of cloud water does not change theta_l. p3_iparam selects
    the warm-rain formula (default Seifert-Beheng 2001). New cases:
    dycoms2_rf02_p3 and rico_p3.
    
    Tested locally with gfortran 10: debug, release and single-precision
    builds pass the standards check. dycoms2_rf02_p3 runs 6 h in all three
    builds; with p3_iparam = 3 (KK2000) its autoconversion and rain number
    match CLUBB's KK case closely. rico_p3 runs 72 h without ice but forms
    almost no rain because grid-mean cloud water is small in partly cloudy
    layers; passing in-cloud values is the next step. Intel/NVHPC builds
    and Jenkins not run. Existing schemes are unchanged.

    * Pass CLUBB's cloud fraction to P3 for in-cloud process rates
    
    P3 received only grid means, so in partly cloudy layers it computed
    autoconversion from cloud water spread over the whole grid box.
    Autoconversion grows much faster than linearly with cloud water, so the
    rate was far too small, and rico_p3 produced no rain.
    
    P3 computes cloud processes from in-cloud values when its subgrid cloud
    and precipitation fraction option (SCPF) is on, but then estimates the
    cloud fraction itself from grid-mean relative humidity. In rico_p3 that
    estimate is about 20-30 % where CLUBB's cloud_frac is 1-3 %, so the cloud
    water is still spread too thin and the case still gives no surface rain.
    p3_main now takes an optional SCF_host argument, and compute_SCPF uses
    it in place of that estimate, with saturated cloudy air and the
    remaining vapor in the clear part. The CLUBB driver passes cloud_frac
    and turns SCPF on.
    
    P3 still derives the rain fraction with its own overlap. Rain gets the
    cloud fraction of the topmost level with rain, and that area is not
    extended where the cloud widens below. CLUBB resolves the cloud top over
    several thin levels with cloud fractions near 1 %, so in RF02 rain kept
    about 1 % of the area through the fully cloudy layer. In host mode, the
    rain fraction inside cloud is now at least the cloud fraction.
    
    Using CLUBB's own precip_frac as P3's rain fraction would complement
    this, e.g. to give P3 with KK and CLUBB's KK the same rain area. It is
    not part of this change.
    
    Results (second-half means, release gcc double, against 548436cd7):
    - rico_p3 surface precipitation 0 -> 0.09 mm/day (SB2001); with
      p3_iparam = 3 about 0 -> 0.58 mm/day, against 0.49 mm/day for CLUBB's
      KK rico case.
    - dycoms2_rf02_p3, where cloud fraction is about 1, changes little
      (peak rrm 1.3e-8 -> 1.6e-8 kg/kg).
    RF02 and RICO also ran without errors in a gcc debug double build.
    No regression test runs P3.

    * Add P3 rime ice hydrometeor indices to hm_metadata_type
    
    P3 describes ice with four fields per category: mass, number, rime mass
    and rime volume. CLUBB's hydrometeor set has slots for ice mass and
    number (iiri, iiNi) but none for the two rime fields, so P3's ice could
    not be carried as CLUBB hydrometeors.
    
    hm_metadata_type gets iiqirim and iibirim (PDF indices iiPDF_qirim and
    iiPDF_birim), and init_pdf_hydromet_arrays_api takes them as two new
    required arguments after iiNg. Schemes without rime pass -1. This
    changes a host-facing API: host models must add the two arguments.
    
    The fields are named after P3's variables, qirim and birim, so that the
    two-letter codes used to build stats names (K_hm_qi, wpqip, ...) do not
    collide with rim. Rime mass is part of rim, so both fields have
    l_mix_rat_hm = false: they are not counted as water, borrowed from in
    hole filling or returned to vapor when small. clip_hydromet_conc_mvr
    clips them at zero instead of treating them as number concentrations.
    They have no default correlations (taken as uncorrelated) and use the
    ice values for hmp2_ip_on_hmm2_ip.
    
    The Python API's HmMetadata and the JAX corr_varnce_module, index
    mapping, fill_holes and stats copies get the same fields.
    
    Existing schemes are unaffected: rico, dycoms2_rf02_morr, mpace_a,
    mpace_b, rico_silhs, dycoms2_rf02_p3 and rico_p3 are bit-identical to
    the previous commit (release gcc double, full runs). G_unit tests and
    the Python API pytests pass. In the JAX pytests, the only failures
    (test_runtime_interface_has_no_fortran_fallback and the file-name
    parity test) also fail before this change; they come from P3 having no
    JAX port yet.

    * Carry P3 ice in CLUBB with l_ice_microphys
    
    P3 could only run warm: CLUBB had no fields for its ice, so the driver
    passed ice as zero and stopped when P3 formed any.
    
    With l_ice_microphys, the P3 setup now uses six hydrometeors: rain mass
    and number plus P3's ice mass, ice number, rime mass and rime volume
    (rim, Nim, qirim, birim). The driver passes them to p3_main and returns
    their changes as tendencies; P3 sediments ice itself.
    
    - Tolerances: P3 nucleates ice far below CLUBB's ri_tol (1e-10 kg/kg),
      and CLUBB returned that ice to vapor every step, so rim stayed zero in
      mpace_b_p3. The four ice tolerances are scaled to P3's smallest ice
      mass, 1e-14 kg/kg.
    - Cloud fraction: P3 keeps ice inside its cloud fraction, so with ice it
      gets max(cloud_frac, ice_supersat_frac). A new optional p3_main
      argument SLF_host gives the liquid part (cloud_frac); it is saturated
      with respect to liquid and the rest with respect to ice.
    - theta_l: freezing and deposition heat the air. The freezing rate comes
      from P3's heat budget (temperature and vapor change), not from the
      change in ice mass, which includes ice falling between levels.
    - precip_rate_sfc includes P3's liquid-equivalent solid rate, and
      eff_rad_ice is output.
    
    New preset mpace_b_p3: the MPACE-B mixed-phase Arctic stratocumulus with
    P3 and a prescribed 30 /cm3 droplet number.
    
    Results: warm P3 runs are unchanged (dycoms2_rf02_p3 and rico_p3
    bit-identical to the previous commit, release gcc double); mpace_a is
    also bit-identical. mpace_b_p3 runs for the full 12 h in debug and
    release gcc double builds. Ice reaches 8e-5 kg/kg and 1e4 /kg, but the
    cloud glaciates: LWP falls from 0.22 to about 0.02 kg/m^2 within 6 h,
    while Morrison (mpace_b_silhs without SILHS) keeps about 0.14 kg/m^2
    with about 10x fewer ice crystals. The cause, likely P3's ice
    nucleation for this case, is not yet investigated.

    * Remove the P3 rain-fraction floor
    
    With CLUBB's cloud fraction in P3, the rain fraction inside cloud was
    held at no less than the cloud fraction. Without that floor, P3 gives
    rain the cloud fraction of the topmost level with rain and does not
    extend it where the cloud widens below. CLUBB resolves the RF02 cloud
    top over several thin levels with cloud fractions near 1 %, so rain
    covers about 0.5 % of the fully cloudy layer.
    
    A comparison with the SAM LES of RF02 (DYCOMS_RF02_128x128x96_dr_sed)
    does not support the floor. It spreads the rain over the whole cloud
    and lowers accretion, moving surface rain further below LES. All CLUBB
    RF02 runs, Morrison included, have about half the LES liquid water path
    and far too little autoconversion, so this case cannot tell which rain
    fraction is right. compute_SCPF uses P3's own rain fraction again; only
    SCF_host and SLF_host remain as CLUBB changes.
    
    CLUBB still passes cloud_frac: P3's own estimate is about 20-30 % in
    rico_p3 where CLUBB's cloud_frac is 1-3 %, and with it rico_p3 gives no
    surface rain.
